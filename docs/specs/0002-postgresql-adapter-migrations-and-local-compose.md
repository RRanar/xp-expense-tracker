# Spec 0002: PostgreSQL adapter, migrations and local compose

## Goal

Milestone 2, first half, of RFC 0001. Give the expense ledger a real, tested persistence layer: a PostgreSQL implementation of the `expense.Repository` port that passes the same contract as the in-memory fake, versioned migrations run as a separate step, a least-privilege database role, and a local compose setup. The gRPC server that uses it is spec 0003. The owner gets a trustworthy storage layer with failure behaviour that has been tested, before any transport depends on it.

This spec was split from the combined "gRPC server and PostgreSQL" milestone because the combined work was about 27 acceptance criteria, too large for one review.

## Scope

In:

- **Domain additions.**
  - Length limits on `category` (64), `merchant` (128) and `note` (1000 characters). The numbers are defaults the owner tunes.
  - `expense.ErrConflict` (an id that already exists) and `shared.ErrUnavailable` (a dependency cannot be reached).
  - `CreatedAt` is normalised to UTC and truncated to microseconds when built, so an entity equals what PostgreSQL returns.
- **`internal/infrastructure/postgres`**: the repository adapter on `pgx` (pure Go, no cgo), queries generated by `sqlc` from `db/queries/`, with `Ping` and `CheckSchema` for the composition root.
- **Migrations** with `goose` in `db/migrations/`, plain SQL, reversible, expand-then-contract, run as a separate step and never at application start (ADR 0005, confirmed here: **goose**).
- **Database roles**: a migration role (owns the schema) and an API role (data access only), created by `db/roles.sql`, which compose and the tests both use.
- **Shared repository contract suite** in `internal/testsupport/repositorycontract`, run against both the in-memory fake and the Postgres adapter. The in-memory fake is updated to satisfy it (it currently overwrites on `Save`).
- **A controllable TCP proxy** in `internal/testsupport/` for outage drills.
- **Local compose** in `deploy/compose/`: PostgreSQL bound to loopback, plus a one-shot migration job; credentials from an untracked `.env` generated by a make target.
- **Integration tests** with testcontainers-go against real PostgreSQL (ADR 0005), behind the `integration` build tag.
- **Architecture checks**: `internal/archtest` extended for the new packages, plus a mechanical check that no SQL text lives in hand-written Go.
- **Benchmark** of the repository operations, recorded in `docs/benchmarks/`.
- CI: generated-code check, integration job, pinned tool installs. `go.mod`, `go.sum`, Makefile, README and `.gitignore` updates.

Out:

- The gRPC server, interceptors, dev identity, error mapping to status codes, health, metrics and alert rules: spec 0003 (outline in Links). The error taxonomy added here (`ErrConflict`, `ErrUnavailable`) is what that spec maps.
- Authentication, rate limiting, `ExportMonth` streaming: milestone 4.
- Outbox table, `wal_level=logical`, Debezium, Kafka, budgets: milestone 3.
- Dockerfile, Cloud SQL, TLS configuration of the deployed database, backup and restore test: milestone 5 (ADR 0005 puts the restore test before the first deployed demo).
- Concurrent-update detection (optimistic locking). `Update` is last-write-wins; recorded as a known limitation and an open question.
- An idempotency key for `CreateExpense`: open question for spec 0003.
- Any change to `api/proto`: none planned. If one is needed it is additive and checked by `buf breaking`.

## Acceptance criteria

1. Given a clean clone and no container runtime, when `go build ./...`, `CGO_ENABLED=0 go build ./...` and `go test -race ./...` run, then all pass. Given the `integration` tag and no reachable container runtime, when the integration tests run, then they **fail loudly** rather than skip.
2. Given `NewExpense`, `Reconstitute` or `Update` with a category over 64, a merchant over 128 or a note over 1000 characters, when called, then each returns an error wrapping `shared.ErrInvalidInput`; values exactly at the limit are accepted; limits count characters, not bytes.
3. Given a `CreatedAt` built from a time with nanoseconds and a non-UTC location, when read back, then it is in UTC with microsecond precision, and an expense saved and reloaded through PostgreSQL equals the original.
4. Given an id that already exists, when `Save` is called with it, then `expense.ErrConflict` is returned and the stored record is unchanged, for the in-memory fake and for PostgreSQL.
5. Given the shared contract suite, when run against the in-memory fake and against the PostgreSQL adapter, then both pass it unchanged. The suite covers: save and reload with every field including the UUID and created time through a fresh connection pool; owner isolation for find, list, update and delete; ordering by expense date then id; category filter and inclusive date range; page size default 50 and maximum 200; an opaque token that resumes after the last item; update and delete; unknown or foreign id returning `ErrNotFound`; a cancelled context returning the context error.
6. Given an id that is not a valid UUID, when `FindByID`, `Update` or `Delete` is called, then `ErrNotFound` is returned, without a database error and without a panic.
7. Given listing in progress, when a new expense that sorts before the current cursor is inserted between two pages, then the next page contains no duplicate and no already-seen item (keyset pagination).
8. Given an empty database, when migrations run up, then the schema exists; when run down, then it is empty again; when run up again, then it succeeds. Given an unmigrated database, when `CheckSchema` runs through the API role, then it returns an error naming the missing migration and creates nothing.
9. Given the API role, when it attempts `CREATE TABLE`, `ALTER TABLE`, `DROP TABLE` or `TRUNCATE`, then each is refused with a permission error; when it runs select, insert, update and delete on the expenses table, then they succeed. Every integration test connects with the API role.
10. Given a direct SQL insert, when the amount is zero or negative, the currency is not three uppercase letters, the category is blank, a text field exceeds its limit or the owner is empty, then the database refuses it (constraints mirror the domain invariants).
11. Given the SQL in `db/queries/`, when `sqlc generate` runs with the pinned version, then the committed generated code is identical (CI fails on any difference); and given a scan of non-generated Go files under `internal/infrastructure/postgres`, then no string literal contains SQL statements.
12. Given the database unreachable, a connection terminated, or a connection-class server error, when any repository method runs, then it returns an error wrapping `shared.ErrUnavailable` within the caller's deadline, and the message contains no connection string, host or password. Given an unexpected SQL error, then the error is not `ErrUnavailable` and not `ErrNotFound`.
13. Given the proxy between the adapter and PostgreSQL is cut, when methods are called, then each returns within its deadline (no hang); when the proxy is restored, then calls succeed **without recreating the adapter**; and an expense whose `Save` was acknowledged before the cut is readable after the restore.
14. Given a statement running longer than the configured statement timeout, when it is hit, then the error wraps `context.DeadlineExceeded`. Given pool settings (maximum and minimum connections, connection lifetime, health-check period, statement timeout), then defaults exist and invalid values are rejected at configuration time.
15. Given a configuration whose SSL mode is `disable`, when validated, then it is rejected unless the explicit local-development flag is set; a connection string never appears in an error message or log line.
16. Given the compose file, when started, then PostgreSQL listens on loopback only, a one-shot migration job applies all migrations as the migration role and exits 0, and the API role has separate credentials. Credentials come from an untracked `.env` produced by a make target from `.env.example`, which holds names and no values; `gitleaks` finds nothing.
17. Given an import of `internal/application` or `internal/transport` from `internal/infrastructure`, or of anything but `domain` and the standard library plus test libraries from `internal/testsupport`, when the dependency-rule check runs, then it fails (fixtures prove it).
18. Given a push or pull request, when CI runs, then it runs the generated-code check, the unit tests and the integration tests on a runner with a container runtime, together with every gate from spec 0001, with `contents: read` permission, SHA-pinned actions and pinned tool versions.
19. Given the repository benchmark, when run with `make bench-db`, then it records, per the benchmarking standard, a result in `docs/benchmarks/<date>-0002-repository.md`: environment, dataset, workload, tool, at least five runs with p50, p95 and p99 for `FindByID`, `List` (unfiltered and filtered) and `Save`, a comparison with the default budget below, and the pass or miss stated plainly.
20. Given the README, when read, then it explains how to run the database and tests locally (including the container-runtime prerequisite), states the known limitations (last-write-wins update, no authentication yet), and states "pet project" with no production claim.

## Domain model

- Aggregate: `Expense` unchanged in shape. New invariants: length limits on category, merchant and note. `CreatedAt` is UTC and microsecond precision.
- Ports: `expense.Repository` keeps its signature. Adapter-level helpers `Ping` and `CheckSchema` are not part of the port; the composition root (spec 0003) calls them.
- Errors: `shared.ErrInvalidInput` (existing), `expense.ErrNotFound` (existing), `expense.ErrConflict` (new), `shared.ErrUnavailable` (new). Mapping to transport status is spec 0003.
- Identity of an expense is a UUID. A string that is not a UUID cannot exist in storage, so lookups by it are "not found".
- Ubiquitous language additions: migration (a versioned, reversible schema change), expand-then-contract (add before remove so each step can be rolled back), keyset pagination (paging by the last seen sort key, not an offset), API role and migration role.

### Schema (migration 1)

`expenses`: `id uuid` primary key; `owner_id text`; `amount_minor bigint` with a check above zero; `currency char(3)` with a check for three uppercase letters; `category`, `merchant`, `note` as `text` with length checks; `expense_date date`; `created_at timestamptz`. One index on `(owner_id, expense_date, id)` serving the list ordering. `owner_id` is `text` because identity (ADR 0012, still Proposed) may change its type later by an expand-then-contract migration. A second index for the category filter is decided from the benchmark, not guessed.

## Security

Assets: financial records (synthetic only), database credentials. Trust boundaries: application to database; developer machine to the local database; CI to its database container.

| Threat (STRIDE) | Abuse case | Mitigation |
|---|---|---|
| Spoofing | Use of a privileged database credential by the application | Separate migration and API roles; the application only ever holds the API role; credentials are injected from the environment (Secret Manager when deployed) and never committed |
| Tampering | SQL injection | `sqlc`-generated parameterised queries only; a mechanical check that hand-written Go has no SQL text (AC 11) |
| Tampering | One owner changes another's expense | Every query carries the owner predicate; the contract suite proves isolation with two owners (AC 5) |
| Tampering | Invalid data written by a buggy caller | Domain validation plus database constraints that mirror it (AC 10) |
| Repudiation | Disputed change | Not in this spec: the audit log arrives with the server (spec 0003) |
| Information disclosure | Connection string or password in an error or log | Adapter errors never include the DSN (AC 12, 15); the local `.env` is untracked; PostgreSQL is bound to loopback |
| Information disclosure | Plaintext database connection | SSL mode `disable` is rejected unless an explicit local-development flag is set (AC 15) |
| Denial of service | Slow or unbounded queries, pool exhaustion | Statement timeout, pool limits, page-size cap, context deadlines (AC 5, 14) |
| Elevation of privilege | The application alters the schema | The API role has no DDL (AC 9) |

Data classification: amount, currency, category, merchant, note and dates are financial (synthetic only); `owner_id` and `id` are internal. Test and demo data are synthetic. Retention and deletion of stored records are decided with the deployed service (milestone 5).

Residual risks, accepted: `Update` is last-write-wins, so two concurrent updates to different fields of one expense can lose one change (single-user pet project; see open questions). The local compose database is plaintext on loopback only.

## Performance budget

Workload model (assumptions the owner tunes, not measurements): five synthetic owners with 10,000 expenses each, so 50,000 rows; a read-heavy mix of about 70% `FindByID` and `List`, 15% `Save`, 10% `Update`, 5% `Delete`; eight concurrent workers; an open-loop generator at a fixed rate so latency is measured from the intended send time.

Default targets, per repository operation on a local PostgreSQL container, percentiles not averages: p95 under 50 ms and p99 under 100 ms. These are defaults to tune and say nothing about the deployed service, whose budget is RFC 0001's p95 under 200 ms for whole requests.

Benchmark: `make bench-db` (the `benchmark` build tag in `internal/infrastructure/postgres`). Method per the benchmarking standard: baseline first, warm-up excluded, at least five runs with the spread reported, the load generator's own saturation checked, one variable at a time. Resource limits are not guessed here; the report records observed container CPU and memory. Results are recorded in `docs/benchmarks/`. A miss is reported as a miss and the owner decides.

## Observability and alerting

Alerting: not applicable — this spec adds a repository adapter, migrations and a local compose file; no server process runs or is deployed, so there are no request SLIs to alert on. The API's SLIs, alert rules and runbooks start with the gRPC spec 0003; database cause signals (replication slot lag, storage) arrive with milestones 3 and 5 per RFC 0001 and ADR 0005.

Logging: the adapter returns errors and does not log; errors are logged once at the transport boundary (spec 0003). The adapter never puts a connection string or a field value in an error message.
